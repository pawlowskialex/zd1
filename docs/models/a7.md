# The A7

B&W's A7 (2011, AirPlay and USB, no dock): the Zeppelin Air's main board MCU and network module (ZZ34088, the same
"interface / Wi-Fi board": `downloads/bw-zeppelin-air-software/a7/SOURCES.md`), its own enclosure, drivers and
voicing. Our firmware has its DSP setup, tells it from the Zeppelin by its bootloader, and builds `a7.fw` for its
first install. **No A7 has run ours yet**: everything below is from B&W's last A7 release (`blobs/a7/a7v20477.fw`,
2.04.77, March 2015) read [RE] and run in the emulator [EMU], or inferred from the Zeppelin with Lightning [INF].
The models side by side: `README.md`.

## What the A7's MCU app does differently

`AZ1_v2-04-77.dmb` ("Dec 12 2014", 0x2EAE4 B at 0x80008000) is another build of the Zeppelin's code ("PSS AZ1"):
Ghidra `python3 -I re/ghidra/setup.py mcu-app-a7` (its `.data` at 0x80033A88, read from its start-up code by
`re/scripts/avr32img.py`). Compared function by function with the ZD1's 2.04.05 (names and addresses normalised)
and traced in the emulator against it (`mcu/stock-firmware.md`, "What the three apps do with the MCU's peripherals"):

- **The same**: the 35 pins it drives and how, the ADC channels (0, 2, 4, 5, 6), the codec, the CS2000, the EEPROM;
  the amp's protections, thresholds included (ADC5's heat, ADC4's, the fault inputs: `FUN_8001a8dc`, `FUN_8001c570`
  = the ZD1's `FUN_8001aa0c`, `FUN_8001c6a0`, the same constants); the board-variant read of ADC2 (`FUN_80014568`,
  < 0x200 variant 1, as the ZD1's `FUN_80014698`: so ADC2 doesn't tell an A7, and the app doesn't need it to).
- **Not there**: the Apple authentication chip (PA02, its reset, stays low; no test of it), the dock (no iAP), the
  copy of the module's network settings in the user page.
- **Its names**: "A7" over USB (the product string; "Zeppelin Air" on the Zeppelin), `A7_Setup_XXXXXX` for the setup
  network; its EEPROM record is version 0x0077.
- **The DSP**: below.

Keys, IR, standby and the sources' code paths compare as the ZD1's in the decompilation but were never run in the
emulator for the A7; the A7's keys are where its enclosure has them, the MCU's pins the same.

## DSP

The A7's ADAU1445 gets **its own download**, sent by `FUN_8001ff4c` (the ZD1's `FUN_80020980`) and extracted by
`python3 -I re/scripts/extract_dsp.py --model a7 re/gen/mcu-app-a7/image.bin re/mcu/extracted/dsp-a7` [RE]: 25
writes (the ZD1's 24, with 0xE240's 26 bytes split into 4 at 0xE240 and 12 at 0xE247, 0xE101 and 0xE141 written as
2 bytes where the ZD1 writes 4 at 0xE100 and 0xE140, and the start's 0xE220 before 0xE228). The emulator's recording
of the stock A7 app is the same, write for write (but the empty write to 0x6000, which the emulated I2C drops)
[EMU 2026-11-21: `zemu run none --mcu A7_FLASH --renode 'zd1:twi.dsp Record "FILE"'`, `re/scripts/dspcmp.py`].

| | ZD1 (and ZD1L) | A7 |
|---|---|---|
| Program RAM (1360 words) | | words 0-689 the same but word 127 (the input stage: the selector, the meter's word 685, the volume and bass stages); 419 of the words from 690 on differ (the output stage: another crossover for other drivers) |
| Configuration | | 0xE100, 0xE140/0xE142, 0xE200/0xE202, 0xE246, 0xE252 differ |
| Parameters (400) | | 47 differ: another voicing (filter coefficients a little apart, two of the ZD1's filters pass-throughs, other gains) |

The runtime controls are the ZD1's [RE]: the volume's safeload to 0x4B with the same 72-step table (`.data` +0x8,
byte for byte), the bass biquad's five words to 0x3F-0x43 from the same five presets, the input selector 0x14 and the
serial routing 0xE080/0xE002 per source, the source gains and selector pairs, all from a parameter-record table
identical to the ZD1's (`FUN_8001ea68` against `FUN_8001f49c`, 0x2A0 bytes). The input meter our firmware reads
(0x031, found on the ZD1 by experiment, never read by stock) is written by the same instruction in both programs
(word 685, in the shared input stage), so it should read the same on an A7 [INF]; its initial value in the download
differs (0x0FFFFFFF on the A7), which the program overwrites if it is a meter there too. If it isn't, the amp's
silence timer never sees silence on an A7 and the amp stays on while a source runs (no harm beyond the heat; `zd1 diag`
shows the level).

Our firmware (`mcu/src/dsp.c`) sends the model's download (`mcu/src/dsp_data.c`, generated by
`mcu/tools/gen_dsp_data.py` from both extractions) and the same runtime writes on every model. On the A7 stand-in
(below) it sends the stock A7 download write for write, then its volume, bass and input [EMU 2026-11-21].

## Its bootloader, and how ours tells an A7

Never read. Held at power-up (ON/OFF while the mains go in), an A7 on B&W's 2.04.77 goes to BL2's web updater with
its light solid white, as a ZD1L does from its HBL's key-hold [HW, an A7 owner, read-only, GitHub issue #2]. B&W
shipped a bootloader release for it (2.00.28, `a7v20028-bsl.fw`, not recovered: "bsl", as the ZD1L
HBL's own "BSL Ready"), the stock A7 app answers the module's request for an MCU update (0x27) the way the ZD1L's does
(ISP_FORCE, the module held, a watchdog reset: `mcu/stock-firmware.md`, B&W's update over the LAN) [EMU], and B&W's
A7 updates are `.fw` files whose MCU part is a `.dmb` for 0x80008000, which the ZD1L's HBL takes from BL2 over SPI.
So the A7's is taken to be a "Net HBL" like the ZD1L's (`mcu/bootloader-hbl.md`), which writes the module's HWID,
"0xA7000000", into its persistent parameters at every start [INF].

Our MCU firmware reads its model from that string (`mcu/src/model.c`, `README.md`): "0xA7000000" in an HBL is an A7.
If the A7's bootloader turns out to carry no such string, or another HWID, ours calls the model unknown, leaves the
DSP in reset and the amp off, and says so (`zd1 info`: "unknown: B&W's bootloader says HWID ..."; the page's Software
panel). Nothing is played through a crossover meant for other drivers. That is also what to report.

In the emulator the A7's bootloader is a **stand-in**: the ZD1L's HBL with its HWID string set to 0xA7
(`tools/zeppelin/fw/bwfw.py`, `hbl_standin`; emulation only, never flashed). `zemu run --mcu ours-a7` runs our
firmware behind it; `bwfw.py a7v20477.fw DIR` puts the stock A7 app behind it.

## The module

B&W's A7 module image is the Zeppelin's module app byte for byte, with HWID 0xA7 in its header, its own factory CnE
(`blobs/a7/module/cne.bin`: `ModelName`/`DeviceName` "A7", the setup network `A7_Setup`, `TCPIPTunnel` off, its own
certificate for the setup page) and resources with the "Prepare for Firmware" panel (`mcu/stock-firmware.md`, "The
three models' module images"). Our module OS reads the HWID from PersParam (`zd1-persparam`'s `unit_model`) and
names itself as the A7's stock software did: "A7 XXXXXX" by default, the AirPlay model "A7".

Its BL2 is unread too, but seen from the network [HW, an A7 owner, read-only, GitHub issue #2]: from key-hold it
comes up on Ethernet in about 10 s with a cable in, else on Wi-Fi after about a minute (the network the speaker
knows), and keeps the interface it started on (a cable pulled: no Wi-Fi, the light blinking blue at ~5 Hz until a
power cycle). Only port 80, GoAhead: `/bl_index.asp` "A7 Setup / Firmware Update", © 2012, **web version 1.16.1.2**
(the ZD1L's: 1.19.4.2, our ZD1's 2010 BL2 has no such pages); `/scripts/info.asp` and `/1000/firmware_status.asp`
the installed module (105.9112, 2014-09-23 12:00:20) and host (2.04.77), the latter **without** the ZD1L's
`<Model>`; its page uploads to `/goform/formPostHandler` and confirms with the plain
`formDownloadConfirmationHandler`, and has the ZD1L's `_HWID` refusal text. A plain power cycle starts B&W's software
again. So it is an earlier build than the ZD1L's, with the same `.fw` pages. Not known: whether it has the **expert
confirm** (`firmware_expert.asp`, `formExpertDownloadConfirmationHandler`), which is the only confirm a modified image
burns through on the ZD1L's (`module/boot-chain.md`, "The ZD1L BL2"), and which the page and `bl2web` send.
`bl2web` asks for that page before it uploads anything and stops if it isn't there; the page can't tell (no-cors),
so on an A7 `bl2web`'s dry run comes first (below). BL2 holds a `.bcd`'s HWID against PersParam's, so it takes
`a7.fw` and refuses `zd1l.fw` on an A7, and the other way round [RE, the ZD1L BL2].

## The first install: `a7.fw`

`nix build .#a7-fw` (`nix/bw-fw.nix`): `os-a7.bcd` (the stub, the kernel and the release's whole system as the boot
initramfs, the rescue's place: it installs itself into slot A at the first start; HWID 0xA7, the A7's factory CnE, no
resources) and our MCU app, the same as every model's, as `AZ1_v2-04-77.dmb`, version 2.04.77 (release 20477). A
release carries it as `a7-VERSION.fw`. It goes in as `zd1l.fw` does on a Lightning model:

1. Best on Ethernet (BL2 up in ~10 s), else on the Wi-Fi it knows (~1 min) [HW]; it takes an address by DHCP.
2. Its updater (BL2's web updater): ON/OFF held while its power goes in, the light solid white [HW]; or, from B&W's
   own software still on it, its setup page's "Prepare for Firmware" over the LAN (`/1000/firmware_prepare.asp`,
   then `/goform/formPrepareFirmwareUpdateHandler?FUOption=LAN`: the module asks the MCU for 0x27, the A7 app goes to
   its bootloader [EMU], the bootloader starts the module into BL2 [INF]).
3. `python3 tools/zeppelin bl2web IP a7.fw` without `--yes` (writes nothing): BL2's state, its web version, whether
   the expert confirm page is there. Only with it there: `--yes`, or the page's Install (A7, behind a tick:
   "untried").

BL2 sends the MCU part to the HBL first, then burns the module's; the speaker restarts into our software. The way back
is the same with `blobs/a7/a7v20477.fw`, B&W's file. If the A7's HBL takes no `.dmb` the way the ZD1L's does, BL2
should fail before the module part (the ZD1L's sends the MCU part first, and a failed transfer writes nothing
[EMU, the ZD1L]), leaving B&W's software in place.

In the emulator, with the stand-ins (a stock A7 from `emu/tools/stockunit.py OUT blobs/a7/a7v20477.fw`: the test
unit's NAND with HWID 0xA7, the ZD1L's BL2 and the A7's module image; the stand-in HBL and the A7's app): see
"Emulator runs" below.

## Emulator runs

- **The first install, end to end** [EMU 2026-11-21, a stock A7 from `emu/tools/stockunit.py /tmp/a7unit
  blobs/a7/a7v20477.fw`, held at power-up, the page's requests (`host/web/test/zd1l.mjs`, `bl2.js`) with `a7.fw`:
  `zemu run /tmp/a7unit/nand.bin --nand --mcu /tmp/a7unit/mcu_flash.bin --fwd 18080:80 --quantum-us 100 --renode
  'zd1:flashc BootprotSize 0x8000' --renode 'zd1:board Pins "0:PA08=0,1500:PA08=1"' --wait mcu 'BSL Ready' --sleep 30
  --host 'node host/web/test/zd1l.mjs host/web/www 127.0.0.1:18080 a7.fw'`]: the stand-in HBL wrote HWID
  0xA7000000, BL2 answered every request and took the confirm, sent the MCU part to the HBL ("ReceiveHostFirmware() -
  Done"), burned the module image, and the HBL restarted into our app; the rescue installed itself into slot A, our
  OS started from slot A and met our MCU firmware on the link. With the stand-ins for the A7's BL2 and bootloader:
  what it shows is that `a7.fw` is put together right, not that an A7 takes it.
- Our firmware as an A7 [EMU 2026-11-21]: `zemu run none --mcu ours-a7 --renode 'zd1:twi.dsp Record "FILE"' --at-once
  --sleep 8`: `[model] A7 (B&W's bootloader, HWID 0xa7)`, `DSP download: ok`, the stock A7 download write for write.
  `--mcu ours` and `--mcu ours-zd1l`: Zeppelin Air / Zeppelin Air with Lightning, the ZD1 download as before.
- An HBL with another HWID (the stand-in with 0x42): `[model] unknown model`, `DSP download: FAILED rc=-3`, and a
  volume key's wake leaves PB09 (the amp's supply) low; with the A7's it goes high, then PB16 (unmute) 2 s later
  [EMU 2026-11-21, `--renode 'zd1:board Pins "6000:PB06=0,6300:PB06=1"'`].
- Our OS on an A7's NAND (the test unit's `nand_os.bin` with PersParam's HWID set to 0xA7) with our MCU firmware
  behind the A7 stand-in: the rescue into slot A, slot A started; `zd1 info` says `model    A7`, the speaker's name
  "A7 000042" (`zd1-settings get name` the same) [EMU 2026-11-21: `zemu run NAND --nand --mcu ours-a7 --wait console
  '\[os\] up' --sleep 40 --host 'zd1 info' --sh 'zd1-settings get name'`, in `nix develop`].

## What an A7 has to show

In order, each with the way back ready (`blobs/a7/a7v20477.fw` through BL2 from key-hold, which an A7 has shown):
1. `bl2web`'s dry run against its BL2 (above): the expert confirm there or not. Without it, stop: the plain confirm is
   another path, to be read in its BL2 first (the stock-patch telnet hook ported to 2.04.77 gives a shell from which
   `fburn rd` reads BL2: `stock-patch/README.md`, "Dumping BL2 from an A7").
2. `a7.fw` through BL2; then over USB (the rear USB-B port) `zd1 info`: "model A7", or "unknown" with the HWID its
   bootloader says (then the DSP is held and the amp off, by design).
3. Its bootloader read out, which a running ours allows whatever the model says: `zd1 peek 0x80000000 0x8000 --out
   boot.bin` and the user page (`zd1 peek 0x80800000 512 --out user.bin`; `peek` is gated: a press of ON/OFF when
   it asks, unless it is the new firmware's first start), as a ZD1L owner did
   (`mcu/bootloader-hbl.md`). It settles the HWID string, the key-hold and the SPI XModem, and makes the model's
   detection exact (with the EEPROM record's version, 0x0077 for the A7 app, as a second source: `README.md`).
4. Sound at a low volume first: the crossover is B&W's A7 program, but the output stage has never been heard.
5. The meter (`zd1 diag`: the level falls when the music stops), the keys, IR, the LED.
